# ADR 0005: Kubernetes packaging (Helm on kind), and no AKS

- **Status:** Accepted
- **Date:** 2026-09-29
- **Phase:** 3 (Day 17, containers and Kubernetes)

## Context

The system is five processes:
- the API;
- the LangGraph worker;
- the MCP news server;
- the Streamlit client;
- Postgres and Redis, counted as one.

Docker Compose runs them on a laptop. The goal for Day 17 is to show they can
be deployed like a real service: probes, resource limits, least-privilege
pods, network isolation, and configuration kept apart from secrets. And to
prove it by actually deploying, not just rendering YAML.

## Decision

### One Helm chart, verified on kind

`infra/helm/` deploys every component:
- **api:** a Deployment, a Service, and an Ingress for real clusters.
- **worker:** a Deployment.
- **news:** a Deployment and Service. The MCP server now runs over
  streamable HTTP instead of as a subprocess of the worker.
- **ui:** a Deployment and Service, optional.
- **Postgres and Redis in the cluster:** plain manifests using the official
  images, for demo environments only.

`values.yaml` holds production-leaning defaults: the slim `runtime` image,
real auth, external databases, and an Ingress. `values-local.yaml` switches
on what kind needs.

`infra/kind/up.sh` sets up the cluster, the images, the config and the
release in one command. Verified on 2026-09-29:
- every pod became Ready;
- the NetworkPolicies were enforced, checked by probing from inside pods
  (worker → news open; api → news, ui → Postgres/Redis, news → Postgres
  blocked);
- pods ran as uid 10001 on a read-only root filesystem;
- through a port-forward, `/health` was ok and `/api/v1/*` returned 401
  without a token.
- **a job ran end to end:**
  - an analyst (Gmail account) submitted it through the UI, via
    port-forward, signed in with Entra ID;
  - the critic sent it round for a second pass, and a different user with
    the approver role approved both passes;
  - the report was archived to Blob;
  - its audit trail reads `job_submitted`, 8 × `llm_call`,
    2 × `approval_decided` (approver), `job_completed`.

**I didn't use the Bitnami charts** for Postgres and Redis. In 2025 their
images moved behind a subscription or to a "legacy" repository. And a
demo-only database doesn't justify a dependency chart: two small templates
are easier to read and to trust.

### What the chart enforces

- **Pods run least-privileged:**
  - non-root (uid 10001, as in the Dockerfile);
  - read-only root filesystem, with `emptyDir` for `/tmp` and `$HOME`;
  - all capabilities dropped;
  - no privilege escalation;
  - the `RuntimeDefault` seccomp profile;
  - no service-account token mounted.
- **Probes that tell different things apart:**
  - **api:** liveness on `/livez` (the process serves) and readiness on
    `/health` (Postgres and Redis reachable). A database outage takes the
    API out of the Service; it doesn't restart it.
  - **worker:** an exec probe checks arq's health key in Redis, refreshed
    every 30 s. The probe doesn't import the app, so it stays cheap.
  - **news:** a TCP check on the MCP port.
- **Exactly one worker, with the Recreate strategy.** Crash recovery
  releases stale arq locks on startup, which is safe only with a single
  worker (D-25). A rolling update would briefly run two.
- **NetworkPolicies** (ingress only):
  - only the worker may reach the news server, which has no auth of its own
    and spends the Tavily quota;
  - only the api and worker may reach Postgres and Redis.
- **Config and secrets are kept apart:**
  - Non-secret settings go in a ConfigMap. Changing it rolls the pods,
    through a checksum annotation.
  - The in-cluster Postgres password is generated by the chart, kept across
    upgrades (`lookup`), and never stored in values or git.
  - There are no other secrets to hold: every Azure call is keyless, and
    the Tavily and Langfuse keys are read from Key Vault by the pods that
    need them.
- **Azure identity:**
  - On kind, pods reuse the developer's `az login`. kind mounts `~/.azure`
    read-only into the node, and the `local` image's entrypoint copies it
    into the pod's own `$HOME`.
  - For a real cluster, the chart exposes ServiceAccount annotations and pod
    labels for Azure Workload Identity (Day 18).

### Image hardening: measured, and why the size barely moved

- **Base images** are pinned by digest: the multi-arch python 3.12.14-slim
  and uv 0.12.20.
- **Runtime image:** has no pip/setuptools/wheel and no `uv`, and runs as a
  numeric non-root `USER`. `HEALTHCHECK` runs `python -m app.healthcheck`,
  one check per component, selected by `MIA_COMPONENT`.
- **PDF parsing** (`pypdf`, the text splitters) moved to an `ingest`
  dependency group, so the server image no longer carries a PDF parser.
  Ingestion runs from the host.

| Image | Before | After |
|---|---|---|
| runtime (api, worker, news) | 397 MB | 397 MB |
| local (runtime + Azure CLI; kind and Compose) | 775 MB | 775 MB |
| ui | 587 MB | 591 MB |

**Why the size didn't change:**
- Removing pip in a later layer hides its files but doesn't free the bytes
  in the base layer.
- The big packages are all dependencies of dependencies: `zstandard` comes
  through langsmith via langchain-core, and there's also `uvloop`, two
  Postgres drivers, and the Azure SDKs.
- The one large optional cut, **not precompiling bytecode, would save 57 MB
  (−14%)**. But it doubled import time from 2.1 s to 4.4 s for every
  process start and every exec probe. I kept the bytecode.

So the gains are in what the image *allows*, not its size: a pinned base, no
package manager at runtime, no parser for untrusted PDFs in the server, and
a health check.

### AKS: intentionally not used

The same chart would deploy to AKS unchanged. That's the point of a chart,
and its production-leaning defaults were written for that case. But AKS
costs real money every month the moment it exists, even for a demo:
- a control-plane tier;
- at least one node VM running around the clock;
- a load balancer and public IP;
- managed disks.

It would show nothing kind doesn't already show: the same manifests, probes
and policies. **I chose not to spend money on it.** Day 18 deploys to Azure
Container Apps instead, which bills per use and scales to zero. The Helm
chart remains the portable, Kubernetes-shaped description of the system.

## Consequences

- **Startup order:** on first start the worker may restart a few times
  until Postgres accepts connections. Kubernetes has no start order, and
  the restart is the normal Kubernetes answer. Schema setup is serialised
  with a Postgres advisory lock, so the api and worker can't race.
- **The UI runs one replica**, because a sign-in in progress is held in its
  process (D-64).
- **Ingress:** kind has no ingress controller. Local runs use port-forward
  (the sign-in redirect is `http://localhost:8501` anyway), and the Ingress
  template is exercised by `helm template` / `helm lint` with production
  values.
- **Demo data only:** in-cluster Postgres has no backups and Redis has no
  persistence. If Redis restarts, queued (not yet running) tasks are lost.
  Real deployments use managed services (`postgres.externalUrlSecret`,
  `redis.externalUrl`).
